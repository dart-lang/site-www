SUMMARY

This document proposes taking ownership of the community-built package:skills solution, bringing it into the official Dart/Flutter ecosystem to simplify skill installation for dependencies.

Author: Jacob MacDonald (jakemac53)

Go Link: flutter.dev/go/{document-title}

Created: Mar 19, 2026   /  Last updated: Apr 15, 2026

WHAT PROBLEM IS THIS SOLVING?

Make it as easy as possible for Dart/Flutter users to install skills for their dependencies with no external tooling required (node/npx).

BACKGROUND

Previously we investigated surfacing things via the MCP server. However, the MCP spec doesn't currently support skills (yet), and there was a clear desire for something which works exactly like skills today. Even though this has a future path to supporting skills, it doesn't meet users where they currently are.

There is already an ecosystem solution for skills, package:skills. This solution is already fairly well fleshed out and also already has some momentum behind it.

Audience

All Flutter/Dart users that use coding agents, and the package authors who want to support them.

Glossary

  • Skills: https://agentskills.io
  • MCP: https://modelcontextprotocol.io

OVERVIEW

This doc discusses what we see as the current state of package:skills, and suggests that we take ownership of this package in order to make it an official part of the ecosystem.

At a high level what package:skills does is as follows:

  • Look through your dependencies (or a given git repo) for a skills directory.
  • If one is found, copy the skills from that directory into local project directories based on the specified IDE/agent you would like to use.
  • Keep track in a metadata file information about the skills that have been installed to allow for updating etc.

Note that package:skills is compatible with npx skills in terms of how you define your skills, which means that package authors can set up skills once, and their users can install them with either tool.

Non-goals

  • Directly vendoring skills via MCP (although this could happen in the future)
  • Writing skills to share with non-Dart developers (this will likely just work to some extent but it is not a design goal of this proposal).

USAGE EXAMPLES

See https://pub.dev/packages/skills for how skills are currently defined. We may want to do some tweaks to this, but the general usage will remain the same.

USER[a] EXPERIENCE

Skills are typically expected to be shipped directly with a package. When done this way, then a user or agent can run dart run skills@ and it will automatically discover and prompt to install available skills (from immediate dependencies).

The agentic equivalent of this experience would be:

  • A user asks an agent to add payment services to their app
  • The agent chooses and installs  a package (maybe using mcp tools)
  • The agent prompts the user if they want to install the skills, and if so it invokes dart run skills@.
  • Note: Do we need a skill for this? Or possibly an MCP tool?
  • If pub get, pub add, etc output some indicator that skills are available, we might not need a skill.

DETAILED DESIGN/DISCUSSION

Take over and promote the dart run skills@ command

The skills package will be developed instead under the dart-lang/ai repo at pkg/skills.

We will ship it by simply publishing the package, and runs of dart run skills@ will always use the latest version (possibly with a short delay based on the semantics of that feature, if there are multiple releases in quick succession).

Possible changes to package:skills

The following are some likely changes we would want to implement in the official version of this tool, assuming we can mostly make them backwards compatible and not break the existing ecosystem.

These are not intended to be requirements just starting places for future discussion.

  • Move the cache directory from .dart_skills to .dart_tool/skills. This is the convention for project specific cached information, and is already ignored by default etc.
  • If the goal is to not have this git ignored, it probably shouldn't be a hidden dir.
  • Allow installing skills only from certain packages, and also only certain skills from those packages. We can also support some configuration or saved preferences to bypass this.
  • This would match the npx skill workflow[b][c][d][e] more closely and avoid people getting too many skills installed (they can pick and choose).
  • We should also remember preferences here but need to figure out the exact UX around that.
  • Move the generic install directory to .agents (see official docs).[f]
  • Update flow could use some additional work
  • One nice part about skills is you have the ability to edit them yourself, but currently skills get would bash over those changes.
  • There is already a manifest, we could add a content hash to this and before upgrading we would check if the skill still has its original content hash. If it doesn't, we should prompt the user and ask if they want to overwrite their local changes.

Security

Skills can be a vector for prompt injection attacks. For pub packages, we rely on the github advisories database to alert people about any reported security concerns, and this will cover the installing skills directly from packages use case.

We should also consider respecting this advisories database when installing skills directly from git repositories.

POSSIBLE FUTURE WORK

Add skills command to the MCP server

We should consider adding a skills tool to the MCP Server, which would have the same subcommands as the skills CLI.

This would use elicitation in order to enforce a user intervention point - it can surface all the questions the CLI would, get explicit approval to install skills, choose the skills to install, etc. This would provide a safer install path for skills which is still gated on explicit user approval.

This will also serve as a way to front load into the context knowledge of Dart skills more generally, which should encourage agents to try and install and use these skills more pro-actively.

Add a callout in pub commands

When running various pub commands, especially add but also potentially get and upgrade, we should detect if a package has a skills directory, and at least notify the user that they could do dart skills add <package> to install those skills.

We could also consider settings as well to automatically install or update skills, or an interactive prompt in the pub tools.[g][h]

Note: Given that AI is in general a contentious topic/tool for some, we must have an opt out mechanism as well before adding notifications like this. The steps to opt out should be clearly listed next to the warning.

FAQ

Why should Dart take official ownership of the skills package?

Official ownership allows the team to provide unified AI direction[i][j][k][l], integrate deeper hooks for current and future agentic tooling, gather analytics, and create a more Dart/Flutter-friendly installation process.

We believe that ensuring AI is highly capable of leveraging our ecosystem is a problem that is critical to the AI assisted developer journey that our team should solve and provide guidance for. Additionally by having a third party own it, we risk community abandonment. Right now this package is getting popular but it’s not so widely used that taking it over would be as much of a lift as later on if we decided to.  

While taking ownership introduces a maintenance burden, increases community reliance on our team for PRs, and presents a minor licensing hurdle—which can be mitigated by requesting a switch to an MIT license—the strategic necessity of controlling and optimizing this core AI feature outweighs the cons[m][n][o].

How would we take over the skills package from the serverpod team?

They have agreed to transfer the publisher to us. We would move development into a dart-lang repo (probably dart-lang/ai but that is TBD).

How would we determine what work they would still agree to if we moved where that package was hosted?

We should probably not assume they will continue to contribute. But we will make it clear that we accept contributions from them and any others who want to.

Should the flutter and dart team be publishing skills using the skills folders today?

For non-mono repo pub packages (not SDK packages) - yes, most likely. This is how npx skills works as well as dart run skills@. You can provide something that works today and also in the future in this manner.

For SDK packages or any mono repo this may be trickier, feel free to reach out on a case by case basis as there are tradeoffs.

Should we rename the package:skills name to something other than skills? It will have bad seo and is highly likely to conflict with another project somewhere?

Sure it might have bad SEO but it is a very easy to discover name and also a short name, and also aligns with npx skills. I don't think the SEO matters much, and it won't have that issue on pub.dev or when using the MCP server to search packages (also searches pub.dev).

How do package authors separate the skills they use for development from the ones they publish for their users to use?

Packages for your own development should be directly developed in the directories that your agent expects them at, so .agent/skills etc. Skills for your users live under a top level skills/ directory and will not be loaded by your agent (unless you install them using dart run skills@).

OPEN QUESTIONS

  • I have some general concerns around the scalability and security concerns of maintaining our own registry, and we likely wouldn't want to point at the serverpod registry directly.
  • I would suggest instead using pub as only official registry here, but allowing users to install skills directly from any git repo also. This would allow installing skills that are not dart/flutter specific still.[p]
  • Or, we could just allow you to bring your own registry, but not maintain one ourselves.
  • Resolution: We will not ship with built in registry support.
  • Should we provide a way for a package to explicitly market itself as supporting skills for another package or category? Or visa-versa, a package to point directly at its pub package containing skills?
  • Using packages versus git repos gives us semantic versioning.
  • We could promote a "skills" topic as a way of signaling a package provides skills.
  • Should we use symlinks or does package:skills use symlinks? We could end up dirtying the pub cache accidentally.

OWNERSHIP

Under this proposal the package would be developed in a dart-lang repo[q][r][s][t], and would require a googler review.

However, we would explicitly like the serverpod team to continue to be the primary maintainers, to the extent that they are still interested in doing so.

TESTING PLAN

Mostly unit tests in the repo, with some light tests for the dart tool to ensure it handles the "not installed" flows correctly.

OTHER OPTIONS CONSIDERED

Top level dart skills [u][v]command

This command would be a simple wrapper around dart run skills@, and will not be developed in the SDK. The skills package will be developed instead under the dart-lang/ai[w] repo at pkg/skills. This mono repo is pulled into the Dart SDK via DEPs, but we will not actually add the pkg/skills package to the set of available packages (so it can have any dependencies it wants).

Similar to how dart test works, it will detect if you have not yet installed the skills package, and prompt  you to run dart pub global activate skills.

Some benefits of having this be a dart cli command include:

  • Better discoverability than a standalone package since it is a part of the dart CLI and will show up in dart –help etc.
  • We can collect analytics if it is a part of the dart tool using existing permission models, and don't need a separate PDD or changes to the existing one.

Why? What can we add, that nobody else can?

The Dart _ecosystem_ is public, anyone can write this package (and they did).

If we think there should be a package like this, and nobody else writes one (or doesn't do it well), I can see why we would want to make a good solution.

And if the existing authors of `package:skill` don't want to keep supporting it, or are not up for a high SLO, it makes sense that we will do it, to makes sure such a package exists.

But that doesn't mean that it has to be a Dart team owned, branded and endorsed package.

There is a risk to being "the official solution" in an environment where changes happen all the time.

Agents can use the package no matter who owns it. And if someone else can make a better tool, and make agents use that instead, we've all won!

I'd at most put this in `dart.tools`, but probably start out in `dart.labs`. Not in `dart.dev`. We are not certain enough about the content and form to make the kind of long-term promise that comes with that.

Tell the community that "here is one way to do it", but don't make any claim that it's necessarily "the best way" or "the official way". Not yet.
